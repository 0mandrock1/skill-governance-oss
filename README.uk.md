# skill-governance-oss

Специфікація управління плюс три лінтери для **колекцій** Claude Skills — один скіл фреймворку
не потребує, двадцять скілів, що ділять стейт, креденшиали й тригер-простір — потребують.

На реальній колекції зі 116 скілів лінтери знайшли:

| | FAIL | WARN |
|---|---|---|
| `validate_registry.py` — власність стану | **37** | 0 |
| `lint_dependencies.py` — контракти успадкування | 0 | **10** |
| `audit_triggers.py` — колізії тригер-фраз | 0 | **12** |

Повний розбір, з трьома дефектами показаними цілком і тим, як їх спіймав кожен лінтер: [CASE.md](CASE.md).

## Запуск

Без інсталяції — клонуй і запускай проти власної теки скілів.

```bash
python3 scripts/audit_triggers.py     --skills ~/.claude/skills
python3 scripts/lint_dependencies.py  --skills ~/.claude/skills
python3 scripts/validate_registry.py  --skills ~/.claude/skills --registry ~/my-registry.md
```

Python 3.8+, лише стандартна бібліотека. `FAIL` блокує, `WARN` інформує. Перший запуск на
існуючій колекції очікувано буде потворним — кожен `FAIL` це дефект, який уже там був, мовчки.
Скопіюй `references/state-registry.template.md`, щоб почати власний (приватний, ніколи не
закомічений) реєстр.

Щоб встановити сам фреймворк як живий скіл у власній колекції (щоб він реально вантажився
за `ENFORCEMENT.md`), скопіюй `skill-creator-framework/`, `references/` і `scripts/` з кореня
цього репо у свою теку скілів, лишивши їх сусідами — інакше відносні посилання всередині
`skill-creator-framework/SKILL.md` не резолвляться.

## Що ловлять ці лінтери, чого не ловить ніхто інший

Два класи дефектів живуть **між** файлами, не всередині жодного окремого — тобто жоден лінтер,
що дивиться на один `SKILL.md`, і жоден рев'ювер, що читає один скіл за раз, їх ніколи не
знайде:

- **Семантичне перекриття тригер-описів.** Два скіли можуть кожен окремо виглядати цілком
  розумно і водночас претендувати на ту саму фразу — тоді жоден не спрацьовує надійно, і модель
  вибирає навмання. `audit_triggers.py` порівнює описи **по всій колекції одразу** — порівняння,
  яке per-file лінтер не може виразити за визначенням.
- **Власність постійного стану.** База даних, тека, ідентичність каналу, креденшиал — кожен
  потребує рівно одного власника-скіла. `validate_registry.py` звіряє декларований у кожному
  скілі блок `## Encapsulation` з окремим файлом-реєстром і репортить сирітські записи,
  незареєстрованих власників і два скіли, що претендують на той самий стан. Жоден
  frontmatter-лінтер чи markdown-лінтер не має поняття "той самий стан, описаний у двох різних
  файлах".

Керівний документ за обома перевірками — OOP-модель, правила успадкування, тред-модель
креденшиалів, життєвий цикл — це [SPEC.md](SPEC.md) (англійською).

## Що всередині

```
SPEC.md                    керівний документ (EN)
references/                trigger-policy, lifecycle, gotchas, шаблон реєстру
scripts/                   три лінтери + спільний парсер + інсталятор enforcement
ENFORCEMENT.md             п'ять шарів, що змушують фреймворк вантажитись на кожну зміну скіла
examples/collection/       скіли, навмисно зіпсовані, щоб лінтери на них FAIL-или
CASE.md                    реальний прогін по 116 скілах цілком
skill-creator-framework/   тонкий покажчик-скіл, щоб `Inherits from:`/`Depends on:` резолвились (див. SPEC.md)
skill-creator-pack/        упакувати скіл (чи набір) для дистрибуції
skill-creator-set/         зібрати кілька скілів у один архів для шерингу
skill-creator-set-unpack/  встановити бандл у цільову колекцію
skill-translator/          перекласти мову тригера скіла, не зламавши тригерингу
skill-rosetta/             звірка термінології між мовами в багатомовній колекції
skill-doc-framework/       конвенції авторства для reference-документів, які скіли читають on-demand
cc-prompt-writer/          генерація промптів/конфігів Claude Code (CLAUDE.md, субагенти, таски)
cc-remote-agent/           базовий контракт делегування headless-роботи на віддалений вузол
mcp-builder/               побудова нових MCP-серверів (гайд Anthropic, без змін)
cowork-agents/             патерни розкидання роботи по субагентах усередині однієї сесії
```
