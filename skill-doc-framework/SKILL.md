# Skill Doc Framework

## Step 0 — MANDATORY

Read `skill-creator-framework` (його `SKILL.md`) повністю в цій сесії, перш ніж
торкатися будь-якого `SKILL.md`. Тригер-простір і контракти спільні — навіть
правка одного рядка ламає колекцію тихо.

Наприкінці, перш ніж вважати зміну готовою, прогнати три лінти й показати FAIL-и
(без відкритих FAIL — не комітити):

```sh
python3 skill-creator-framework/scripts/validate_registry.py --skills . --registry <private state-registry.md>
python3 skill-creator-framework/scripts/lint_dependencies.py --skills .
python3 skill-creator-framework/scripts/audit_triggers.py  --skills .
```


Генератор структурованих методичних документів. На відміну від справжніх Claude Skills (`skill-creator`), результат тут — це **читабельний markdown-документ для людини або для іншого LLM-асистента**, не виконуваний артефакт із YAML frontmatter і живими тригерами.

Використовуй, коли Mark просить задокументувати процес, зробити playbook, чеклист, опис експертизи — і не просить саме працюючий Cowork/Claude Skill.

## Крок 0 — перевір дублікати

Перед тим як писати новий документ — запитай себе: чи це вже покрито існуючим skill/довідником у цій колекції? Якщо так — запропонуй доповнити наявне, а не плодити копію.

## 7 кроків

### 1. Підготовчий аналіз
Визнач конкретну проблему, цільову аудиторію, очікуваний результат. Без цього кроку документ вийде абстрактним "про все й ні про що".

### 2. Базова структура
Назва у форматі `# Skill: [Назва]`, опис 1-3 речення — що це і навіщо, без води.

### 3. Застосування
5-8 конкретних use cases, маркований список. Специфічно, не абстрактно — "follow-up лист клієнту після дзвінка", а не "ділова комунікація".

### 4. Кроки використання
3-7 кроків, нумерація, дієслова у наказовій формі ("Визнач", "Перевір", не "Варто визначити"). Для складних кроків — підпункти. Якщо крок має вагу/пріоритет (як у прикладі API Design Review) — можна додати відсоток.

### 5. Приклади
2-4 приклади різної складності. Формат Input → Process → Output або готовий приклад самого документа в code-block (` ```markdown `). Приклади — це найцінніша частина: без них документ не дає відчуття "як це виглядає в житті".

### 6. Обмеження та застереження
Технічні межі (розмір, кількість кроків), best practices (✅/❌ списком), типові помилки. Чесно вказуй, де метод не працює — це підвищує довіру до документа більше, ніж список переваг.

### 7. Метадані
Версія, категорія, складність, орієнтовний час виконання, залежності, рекомендована періодичність оновлення.

## Приклади (референс)

### Проста навичка
```markdown
# Skill: Email Formatting

## Опис
Структурування та форматування професійних email-повідомлень згідно з бізнес-етикетом.

## Застосування
- Ділове листування
- Запити інформації
- Follow-up листи

## Кроки використання
1. Визнач мету листа
2. Обери тон спілкування
3. Структуруй: привітання → тіло → заклик до дії → підпис
4. Перевір на ясність та коректність
```

### Складна навичка (зважені кроки)
```markdown
# Skill: API Design Review

## Опис
Експертний огляд API-дизайну з оцінкою архітектури, безпеки, продуктивності.

## Кроки використання
### 1. Архітектура (30%)
- RESTful principles, версіонування, консистентність endpoints
### 2. Безпека (25%)
- Auth методи, rate limiting, input validation
### 3. Документація (20%)
- OpenAPI специфікація, приклади, error handling
### 4. Продуктивність (15%)
- Pagination, caching, payload optimization
### 5. Звіт (10%)
- Критичні issues, пріоритизовані покращення
```

Повний приклад "Data Analysis Report" і повний оригінальний шаблон — у Craft-документі
"Skill: Створення навичок за Framework (ChatGPT template)" (референс, не редагувати — джерело методології).

## Шаблон для швидкого старту

```markdown
# Skill: [Назва навички]

## Опис
[1-3 речення про суть та призначення]

## Застосування
- [Use case 1]
- [Use case 2]
- [Use case 3]

## Кроки використання
### 1. [Назва кроку]
- [Деталь]
### 2. [Назва кроку]
- [Деталь]

## Приклади
### Приклад 1: [Назва]
**Input:** [Вхідні дані]
**Output:** [Результат]

## Обмеження та застереження
- [Обмеження 1]
- [Best practice 1]

## Метадані
- Версія: 1.0
- Категорія: [Категорія]
- Складність: [Низька/Середня/Висока]
- Час виконання: [Орієнтовний час]
```

## Обмеження

- Оптимальний розмір: 200-500 слів на документ. Довше — виносити деталі в окремий референс-файл.
- 3-7 кроків. Більше — розбивай на під-документи.
- Це НЕ формат Claude Skill. Якщо мета — щоб документ реально тригерився й виконувався в Cowork/Claude Code, після написання передай результат у `skill-creator` для конвертації в справжній SKILL.md з YAML frontmatter.
- Не вигадуй use cases і приклади з нуля, якщо Mark дав реальний контекст процесу — приклади мають відображати його реальну роботу, інакше документ вийде generic і непридатний до використання.
