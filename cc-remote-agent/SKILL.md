# cc-remote-agent

Абстрактний батько. Транспорт (`exec` / `upload` / `download`), шляхи і дефолтний allowlist задає інстанс. Тут — інваріанти, які інстанси НЕ переписують.

## Коли цей клас, а коли ні

| Ситуація | Куди |
|---|---|
| 1–3 shell-команди, читання, `systemctl status` | `node-a-ssh` / `node-b-desktop` напряму |
| Багатокрокова зміна коду на віддаленій машині | **сюди** |
| Задача потребує читання десятків файлів на тій машині | **сюди** (контекст живе там, не тут) |
| Незалежні шматки роботи в поточній сесії | `cowork-agents` (Agent tool) |
| Треба лише ТЕКСТ промпта, запускати буде людина | `cc-prompt-writer` |

Головний критерій: **де живе контекст**. Якщо для задачі треба перечитати чужий код — хай його читає агент, що стоїть поруч із цим кодом. Кожен `cat` через MCP коштує двічі: у їхньому вікні і в моєму.

## Public Interface (Inter-Skill API)

- `cc_remote_agent.spawn(node, cwd, prompt_md, opts)` → `{run_id, log_path, pid}`
- `cc_remote_agent.poll(node, run_id)` → `{state: running|done|failed, tail, exit_code}`
- `cc_remote_agent.result(node, run_id)` → повний лог + витягнутий фінальний блок
- `cc_remote_agent.cancel(node, run_id)`
- `cc_remote_agent.chain(node, cwd, plan_file, tag)` → `{chain_log, exit_code}` — послідовність ранів в одній робочій копії, крок 4b

Інстанс реалізує лише `node` (транспорт + шляхи), решта — успадковується.

## Крок 1. Промпт у файл, ніколи не інлайном

`ssh_exec` виконує через `/bin/sh`. Багаторядковий промпт з лапками, апострофами й `$` в інлайні ламається мовчки — і ти дізнаєшся про це через 40 секунд по кривому результату.

```sh
mkdir -p {RUNS}/{run_id}
cat > {RUNS}/{run_id}/task.md <<'CCTASK'
...промпт...
CCTASK
```

Heredoc з **лапками** навколо `CCTASK` — інакше `$VAR` і backticks усередині промпта розкриються шеллом.

`run_id` = `{slug}-{YYYYMMDD-HHMMSS}`. Slug з латиниці й дефісів, ≤ 24 символи.

## Крок 2. Структура промпта

Успадковується з `cc-prompt-writer`, Mode 3 (one-off task prompt), без змін:

```
## Goal        — результат, не кроки
## Scope       — що чіпати; окремим рядком що НЕ чіпати
## Approach    — опорні файли, відомі шляхи, ID, порядок
## Verify      — чим перевірити, що спрацювало (команда + очікуваний вивід)
## Done        — критерій завершення + що вивести останнім блоком
```

Плюс два обов'язкові доважки саме для віддаленого запуску:

```
## Report
Останнім блоком виведи рівно:
RESULT: ok|fail
CHANGED: <файли через кому>
NOTES: <один рядок>
```

І verbatim-блок constraints із `cc-prompt-writer` → `references/cc-constraints.md`. Не переказуй його своїми словами.

Worktree ізолює лише git-стан, не файлову систему: агент усередині власного
worktree однаково може дописати чи затерти щось у сусідній робочій копії,
якщо звертається до неї абсолютним шляхом. Ран, що спавниться в окремому
worktree, мусить мати в `## Scope` явний рядок: «працюй лише в межах
`<абсолютний шлях цього worktree>`, не чіпай сусідні робочі копії» — не
покладайся на те, що ізоляція станеться сама.

## Крок 3. Аромати (output styles) — важіль на токени

Дефолт — **caveman** для механічної роботи, **ponytail** для роботи, де агенту треба щось вирішувати.

| Аромат | Що робить | Коли |
|---|---|---|
| `caveman` | телеграфний стиль, без артиклів, без пояснень, без преамбул | міграції, рефактор по зразку, масові правки, деплой |
| `ponytail` | структурований, з явним планом і самоперевіркою перед записом | нова фіча, дизайн API, все, де є вибір |
| `caveman+ponytail` | план ponytail-ом, виконання caveman-ом | довгі задачі на 20+ кроків — **два послідовні спавни**, не один ран: output style читається один раз на старті сесії, а headless `claude -p` завжди одна сесія на ран. Спавн 1 (ponytail) видає план текстом, спавн 2 (caveman) отримує той план у своєму `task.md` і виконує |

**Немає `--output-style` CLI-флага** — це не флаг, це поле `outputStyle` у
settings. Механіка вибору й перевірки стилю на вузлі:

```sh
ls ~/.claude/output-styles/ 2>/dev/null
```

- Файл `{STYLE}.md` **існує** в `~/.claude/output-styles/` на вузлі →
  активувати саме на цей ран, без правки спільного `settings.json` (races між
  паралельними спавнами):
  ```sh
  --settings '{"outputStyle":"caveman"}'
  ```
- Файлу **нема** — інстанс або встановлює його правильно (формат:
  `references/output-style-format.md` — markdown, frontmatter `name` /
  `description` / `keep-coding-instructions: true` для агента, що лишається
  coding-агентом), або, як разовий фолбек без права щось встановлювати на
  вузлі, емулює префіксом першого рядка `task.md`:
  - caveman: `STYLE: caveman. Тільки дії й факти. Без вступів, підсумків, пояснень очевидного. Речення обрубані. Код замість прози.`
  - ponytail: `STYLE: ponytail. Спершу план з 3-7 пунктів у голові, потім виконання. Перед кожним записом — чи мінімальна зміна. Після кожної мутації — перечитати реальний стан.`

Не вигадуй третій стиль, якщо його нема в списку вузла.

**Скільки реально економить** — не заміряно поки що як тверде число; замість
застарілого відсотка тут — активний протокол вимірювання: чергувати
caveman/ponytail на порівнюваних задачах і фіксувати динаміку (запис у
пам'яті Марка, `mem` schema, `procedural`, тег `caveman`/`ponytail`/
`output-style`). Онови цей рядок конкретною цифрою, коли назбирається
достатньо ранів для висновку — не раніше.

## Крок 4. Спавн

Спавниться **не `claude -p` напряму, а обгортка `cc-run.sh`**: вона робить сам
виклик, а після нього витягує рядок `RESULT:` з `out.log` і віддає його в
`{NOTIFY}`. Без обгортки нотифікацію має тільки ланцюг (крок 4b), а одиночні рани
мовчать — і про кінець рану дізнаєшся, лише сам зайшовши в лог.

```sh
cd {CWD} && \
CC_TOOLS="{TOOLS}" CC_TAG="{TAG}" \
flock -n {RUNS}/{slug}.lock -c '
  nohup sh {RUNS}/cc-run.sh {RUNS}/{run_id} {STYLE} {MODEL} \
    > {RUNS}/{run_id}/wrap.log 2>&1 &
  echo $! > {RUNS}/{run_id}/pid
' || echo "BUSY: інший ран з тим самим slug ще працює"
```

Контракт обгортки (`scripts/cc-run.sh`; ставиться на вузол інстансом поруч із
`cc-chain.sh`, шлях — `{RUNS}/cc-run.sh`):

| | |
|---|---|
| аргументи | `<run-dir> [style] [model]`; run-dir мусить уже містити `task.md` |
| `style` | `caveman` \| `ponytail` \| `none` (`none` = без `--settings`) |
| env | `CC_TOOLS` (дефолт `Bash Edit Write Read Glob Grep`), `CC_NOTIFY` (дефолт `{RUNS}/cc-notify.sh`), `CC_TAG` (префікс повідомлення) |
| коди виходу | `0` ok, `2` fail, `3` session limit, `5` тижневий лок, `6` гард дорогої моделі — ті самі, що в `cc-chain.sh` |
| кладе в run-dir | `out.log`, `exit_code`, `usage.txt`, `cost.log` (обидва — якщо на вузлі є `run-usage.sh` / `cc-cost.sh`) |
| нотифікація | best-effort: нема файлу `{NOTIFY}` — крок тихо пропускається, ран від цього не падає і код виходу не змінюється |

### Гард дорогої моделі (`cc-opus-gate.sh`, exit 6)

Ран з `opus` **не стартує** без `CC_OPUS_REASON` — одного рядка про те, яке
архітектурне рішення робить саме цей ран. Перевірка стоїть **до** спавна
`claude -p`, тому відмова коштує нуль токенів. Ланцюг спиняється на першому
такому кроці; гард перевіряє **кожен** крок окремо, бо plan-файл може мішати
моделі по рядках.

```sh
CC_OPUS_REASON="розводить абстракції нового шару" sh cc-run.sh {RUN_DIR} none opus
```

Підстава (заміри 24–27.08, 99 ранів у `swarm.runs`): 95%+ обсягу будь-якого
рану — це `cache_read` зростаючого транскрипту, який пересилається на кожному
turn. Тому ціна рану визначається **множником моделі**, а не щільністю
`task.md`: opus коштує рівно 5x за токен на всіх статтях (in/out/cache).
Накопичена переплата за opus на ранах, які виконували вже прийняті рішення
(конвертація, верстка, рефактор за зразком), — близько **$527**.

Правило вибору: opus — коли ран **ухвалює** рішення (обирає підхід, розводить
абстракції, шукає причину неочевидного бага). Sonnet — коли ран **виконує** вже
ухвалене. Обсяг роботи й довжина `task.md` на цей вибір не впливають.

`cc-cost.sh` після рану дописує в `cost.log` і `telemetry.log` рядок з
фактичною вартістю і sonnet-еквівалентом — щоб переплата була видима одразу,
а не через тиждень у зведенні.

Матчер `RESULT:` — **той самий**, що в драйвері ланцюга
(`RESULT:[[:space:]]*\**[[:space:]]*ok`), щоб одиночний ран і ран у ланцюзі не
розходились у тому, що вважати успіхом.

`{NOTIFY}` — такий самий параметр інстанса, як `{RUNS}`. Вузол без нотифікації
(десктоп, Pixel) нічого не патчить: там просто нема `cc-notify.sh`, і обгортка
мовчки пропускає крок.

Якщо `{STYLE}.md` нема на вузлі (див. крок 3) — передати обгортці `none` замість
назви стилю й покластись на префіксну емуляцію в `task.md`, не передавати
неіснуючу назву (Claude Code мовчки ігнорує невідомий `outputStyle`, а не падає —
тиха деградація).

Обгортки на вузлі ще нема → або інстанс кладе її туди (файл лежить у
`scripts/cc-run.sh` цього скіла), або, як разовий фолбек, `claude -p` іде голим
за старою формою — але тоді **скажи Марку рядком, що цей ран без нотифікації**,
не давай мовчазної деградації.

Правила, які не обговорюються:

1. **`flock -n` по slug.** Два агенти в одній робочій копії = зіпсований git-стан. Зайнято — не чекай, поверни `BUSY` і скажи людині.
2. **`nohup ... &`.** Синхронний виклик через MCP відвалиться по таймауту на будь-якій змістовній задачі. Спавн повертає керування за секунду.
3. **`--permission-mode acceptEdits`**, не `bypassPermissions`. Дозволяє правки й дозволені інструменти, але не робить агента безмежним.
4. **`--allowedTools` явний і вузький.** Дефолт бази: `Bash Edit Write Read Glob Grep`. Кожен MCP — окремим рішенням інстанса, не «про всяк випадок».
5. **Модель.** Не хардкодь. `--model sonnet` для механіки — свідома економія; для дизайну не вказуй нічого і бери дефолт вузла.

## Крок 4b. Ланцюг — кілька ранів в одній робочій копії

`flock` з кроку 4 тримає **slug**, а не репо. Два рани з різними слугами в одному каталозі проходять замок і псують git-стан одне одному. Тому рани, що чіпають ту саму робочу копію, — не батч, а **ланцюг**: строго один за одним, кожен наступний від гілки попереднього.

Не пускай ланцюг вручну, чекаючи людину між ранами: пауза між ранами дорожча за самі рани. Драйвер — `scripts/cc-chain.sh`:

```sh
sh scripts/cc-chain.sh {CWD} {PLAN} [tag]
```

`{PLAN}` — рядок на ран, `slug|style|/abs/path/task.md`. `style` — `caveman` | `ponytail` | `none` (без `--settings`, контрольна група). `{RUN_ID}` у `task.md` підставляється реальним id на спавні.

Інваріанти драйвера, які інстанси не переписують:

1. **Стоп на першому рані без `RESULT: ok`.** Гілка лишається як є, для розбору. Три рани поверх кривого фундаменту коштують дорожче, ніж один ран без прогресу.
2. **`session limit` — окремий код виходу (3), не `fail`.** Це «прийди пізніше», а не провал задачі; вцілілі гілки лишаються, добити можна одним ранем.
3. **Гілка від гілки.** Кожен ран стартує з `git checkout -b cc/{run_id}` від поточного HEAD, тобто від результату попереднього. Не від main.
4. **Полінгу всередині ланцюга немає.** Драйвер сам ходить від рану до рану; людина читає лог ланцюга, а не логи ранів.

Черга за вже запущеним ланцюгом ставиться окремим воркером, який чекає завершення процесу і **перевіряє, що попередній ланцюг дійшов до кінця**, перш ніж пускати наступний. Приклад — `references/chain-runs.md`.

**Розводити рани треба не лише по гілках, а й по цілях.** Два рани, що пишуть в одну веб-теку, зіпсують одне одному результат навіть будучи послідовними — а якщо людина в цей час перевіряє ту теку, ран стирає предмет перевірки. Деплой-ціль ланцюга називай у промпті явно, разом із тим, які теки чіпати заборонено.

Ціль ширша за файлову теку. Перед паралеллю перевіряй колізії по трьох осях:

| Вісь | Приклад колізії |
|---|---|
| шляхи запису | дві гілки пишуть той самий файл поза узгодженими чанками |
| ціль деплою | `staging` і `prod` в одну `{deploy-root}/{app}` |
| **зовнішній ресурс з лімітом** | два скрипти в один rate-limited API |

Третя вісь — найтихіша: `flock` її не бачить взагалі. Два періодичні скрипти з **різними** lock-файлами, що ходять в один API, замок проходять обидва і разом вибивають 429. Спільним ресурсом однаково є зовнішнє API, шаред-БД, один Telegram-бот-токен, одна черга. Якщо ресурс спільний — послідовно, навіть коли шляхи запису різні.

## Крок 4c. Робота, довша за ран — демоном, а не всередині рану

Обхід зовнішнього API по сотнях сутностей, масовий переембединг, будь-який прохід
із тротлінгом — це години. Ран стільки не живе. Спроба пройти корпус усередині
рану дає найдорожчий з можливих провалів: контекст вигорає на однакових ітераціях,
ран падає по таймауту, робота не зроблена й прогрес не збережений.

Правильна форма — ран **готує і запускає**, а не виконує:

1. пише скрипт, що робить прохід, з **чекпоінтом у БД** (таблиця `{job}_sync`:
   одиниця роботи, `status pending|done|error`, `attempts`, `error`);
2. піднімає його демоном — `systemd` unit (`Type=simple`, `Restart=on-failure`)
   або `setsid nohup` під `flock`; демон мусить пережити обрив ssh-сесії;
3. робить **два заміри лічильника** `done` з паузою і переконується, що він зріс;
4. виходить.

```sh
A=$(psql -tAc "select count(*) from {job}_sync where status='done'")
sleep 60
B=$(psql -tAc "select count(*) from {job}_sync where status='done'")
[ "$B" -gt "$A" ] || echo "RESULT: fail — лічильник не рухається"
```

**Критерій приймання такого рану — рухомий лічильник, а не завершена робота.**
Ран, що чесно відзвітував «запущено, прогрес іде», зробив свою роботу повністю.

Чекпоінт заразом дає відновлення: обрив на 300-й одиниці не скидає перші 299,
наступний запуск бере наступний `pending`. Без чекпоінта кожна помилка на
зовнішньому боці (429, таймаут, розрив) відкочує прохід у нуль.

## Крок 5. Полінг

```sh
test -e /proc/$(cat {RUNS}/{run_id}/pid) && echo RUNNING || echo FINISHED
tail -c 2000 {RUNS}/{run_id}/out.log
```

Полінг з інтервалом **не частіше 60 с**. Між полінгами роби іншу роботу — не крути порожній цикл, це чистий спал токенів. Довгі рани (10+ хв) віддавай у `notify-tg-schedule` замість сидіння над логом.

`pid` тепер належить **обгортці**, а не самому `claude` — і це правильно: процес
живий, поки не дописано `out.log` і не відпрацювала нотифікація.

Ознака завершення — блок `RESULT:` у хвості логу плюс файл `exit_code` у run-dir
(`0`/`2`/`3`). Нема `RESULT:` при мертвому pid → рахуй `failed`, читай останні 100
рядків, не 5000.

## Крок 6. Верифікація — обов'язкова, окремо від агента

Агент, який каже «зроблено», — це свідчення, а не факт. Після `RESULT: ok` **сам** звір стан транспортом:

- Код: `git -C {CWD} diff --stat HEAD~1` або `git status --short`
- Сервіс: `systemctl is-active X` / `pm2 jlist | jq`
- HTTP: `curl -sS -o /dev/null -w '%{http_code}' <url>`
- БД: `SELECT` по зміненій таблиці

Не збігається з `CHANGED:` — не «майже вийшло», а `failed`.

**Критерій — стан системи, а не наявність написаного.** Ран, що створив файл зі
скриптом, ще нічого не зробив. У `## Verify` промпта формулюй перевірки як
рядки в таблиці, HTTP-коди, `is-active`, лічильники — і окремим рядком забороняй
зараховувати `--dry-run` за роботу. Інакше отримаєш `RESULT: ok` при нулі рядків
у базі.

**Заміна періодичної задачі зобов'язує прибрати попередника.** Ран, що поставив
новий крон/таймер замість старого, мусить явним кроком видалити рядок
попередника і показати `crontab -l` (чи `systemctl list-timers`) **після** правки.
Інакше два покоління скрипта живуть паралельно й б'ються за спільний ресурс —
різні lock-файли їх не розведуть (крок 4b).

Тест, що не впав при навмисному зламі коду, — не верифікація, а недоведена
теза. Вимагай у `## Verify` промпта явного циклу: зламав навмисно → тест
впав → відкотив злам → тест знову зелений. Без цього доказу тест міг просто
нічого не перевіряти.

Харнес мусить покривати **всі** заявлені цілі задачі, не лише головну.
Реальний провал: 21 перевірка на трьох телефонних viewport-ах була зелена,
а десктопний вигляд ліз — приймалка не дивилась на екран, на який дивиться
людина. Перед `RESULT: ok` звір список цілей з `## Goal`/`## Scope` промпта
з тим, що харнес реально перевіряє; ціль без відповідної перевірки —
привід не довіряти `ok`.

Перш ніж визнати ран **брехнею** (агент сказав `ok`, а факту нема) —
перевір сусідні робочі копії й worktree. Симптом «файлів немає там, де
очікував» так само пояснюється тим, що агент (особливо у worktree, крок
4b/worktree-ізоляція вище) записав їх абсолютним шляхом не в ту копію —
а не тим, що він набрехав. Хибний негативний вердикт дорожчий за одну
зайву перевірку `find`/`ls` по сусідніх копіях.

## Крок 7. Відкат

Кожен спавн, що чіпає код, починається з гілки й точки повернення:

```sh
git -C {CWD} rev-parse HEAD > {RUNS}/{run_id}/base_sha
git -C {CWD} checkout -b cc/{run_id}
```

Провал → `git checkout -` + `git branch -D cc/{run_id}` (або `git reset --hard $(cat base_sha)` для брудної копії). Сервіс уже рестартнутий і не піднявся → відкат **і рестарт назад**, у такому порядку. Ніколи не лишай вузол у стані «код новий, процес старий».

Немає git у `{CWD}` → перед мутацією зроби `cp -a {CWD} {CWD}.bak-{run_id}`, після успіху прибери.

## Anti-патерни

- Промпт інлайном у команді → зламані лапки, мовчазна деградація.
- Синхронний `claude -p` через MCP → таймаут посеред роботи, осиротілий процес.
- `--dangerously-skip-permissions` заради швидкості → одного разу дуже дорого.
- Агент без `## Verify` → повертає «ok» на непрацюючий код.
- UI: headless-браузер (Playwright/Puppeteer), НІКОЛИ jsdom — jsdom не має
  движка лейауту, `getBoundingClientRect` там завжди повертає нулі, тож
  будь-який тест на геометрію (позиція, розмір, перекриття) на jsdom —
  фікція, що завжди зелена.
- Той самий slug паралельно → git-конфлікт всередині одного каталогу.
- Полінг раз на 5 секунд → більше токенів на очікування, ніж на роботу.
- `--output-style` як CLI-флаг — такого флага нема в жодній версії; це поле `outputStyle` у `--settings`.
- Покладатись на `flock` як на захист репо — він тримає slug, не робочу копію (крок 4b).
- Чекати людину між ранами ланцюга → очікування довше за роботу.
- Два рани в ланцюзі з однією веб-текою деплою → затирають одне одного і зривають перевірку людині.
- Ланцюг, що йде далі після не-`ok` рану → три рани поверх кривого фундаменту.
- Багатогодинний прохід усередині рану → вигорілий контекст, таймаут, нуль збереженого прогресу (крок 4c).
- Верифікація за фактом написаного коду → `RESULT: ok` при порожній таблиці.
- Новий крон поруч зі старим → два покоління скрипта в один зовнішній API.
- Одиночний ран повз `cc-run.sh`, голим `claude -p` → ран мовчить у кінці, а обіцянка «будь-який ран нотифікує» в `CLAUDE.md` вузла стає неправдою.

## Encapsulation

Owns: каталог ранів `{RUNS}` (шлях дає інстанс), файли `task.md`, `out.log`, `pid`, `exit_code`, `usage.txt`, `cost.log`, `wrap.log`, `base_sha`, гілки `cc/*`, обгортку `cc-run.sh`, драйвер `cc-chain.sh`, гард `cc-opus-gate.sh` і `cc-cost.sh` на вузлі.
Не володіє: робочою копією проєкту, сервісами, credentials — це зона інстанса й самого проєкту.

## Reference Files
- `references/output-style-format.md` — точний формат кастомного output style
  файлу (frontmatter, розташування, як інстанс встановлює його на вузлі, якщо
  нема), для інстансів що бутстрапляться на нову машину.
- `references/chain-runs.md` — ланцюги (крок 4b): формат plan-файлу, коди
  виходу драйвера, воркер черги за вже запущеним ланцюгом, розведення цілей
  деплою. Читати, коли ранів більше одного в тій самій робочій копії.
- `scripts/cc-chain.sh` — сам драйвер ланцюга. Ставиться на вузол інстансом; шлях
  до каталогу ранів береться з `CC_RUNS` (дефолт `$HOME/cc-runs`), тижневий
  лок — з `CC_WEEK_LOCK` (дефолт `$CC_RUNS/.week-locked`). Крім ланцюга сам по
  собі несе: mkdir-ізоляцію по CWD і plan-файлу (exit 4), π-призначення аромату
  зі спільним лічильником, `RUN_TIMEOUT_S` (дефолт 2700) і
  `CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS=0` проти обриву сесії на фоновій задачі,
  авто-коміт незакоміченого перед вердиктом, гейт тижневого бюджету (exit 5,
  fail-open), гард дорогої моделі покроково (exit 6), виклики `cc-telemetry.sh`
  і `cc-cost.sh` після кожного кроку.
- `scripts/cc-run.sh` — обгортка одиночного рану з кроку 4 (виклик + витяг
  `RESULT:` + нотифікація). Ставиться на вузол поруч із `cc-chain.sh`.
- `scripts/cc-opus-gate.sh` — гард дорогої моделі (exit 6). Ставиться на вузол
  поруч із `cc-run.sh`; його відсутність не валить ран, але тоді opus нічим не
  стримується.
- `scripts/cc-cost.sh` — пост-фліт вартість рану + sonnet-еквівалент у
  `cost.log`. Потребує `usage.json` від `run-usage.sh` і `jq`.
