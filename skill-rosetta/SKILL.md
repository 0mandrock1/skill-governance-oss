# skill-rosetta

## Step 0 — MANDATORY

Read `skill-creator-framework` (його `SKILL.md`) повністю в цій сесії, перш ніж
торкатися будь-якого `SKILL.md`. Тригер-простір і контракти спільні — навіть
правка одного рядка ламає колекцію тихо.

Наприкінці, перш ніж вважати зміну готовою, прогнати три лінти й показати FAIL-и
(без відкритих FAIL — не комітити):

```sh
python3 skill-creator-framework/scripts/validate_registry.py --skills . --registry <private state-registry.md>
python3 skill-creator-framework/scripts/lint_dependencies.py --skills .
python3 skill-creator-framework/scripts/audit_triggers.py  --skills .
```


Inherits from: `skill-creator-framework` (naming conventions, checklist, OOP-модель
скілів — читати перед перекладом, там же список parent-скілів `core`,
`purchase-helper`, `cowork-prompt`).

## Що робить

1. **Приймає сирий опис Марка.** Може бути одне речення, мішанина мов, кодові
   назви проєктів, без явної назви скіла чи тригерів.
2. **Спершу шукає match серед існуючих скілів** — звірити з `<available_skills>`
   за description + trigger-фразами (не тільки за назвою — Mark рідко називає
   скіл прямо). Якщо є явний або близький match:
   - Явний match → сказати яким скілом це вже покрито, використати його, **не
     створювати дубль**.
   - Частковий match (нова вісь/тема всередині існуючого домену) → запропонувати
     розширення існуючого скіла замість нового файлу.
3. **Якщо match немає** — перекласти сирий опис у структуровані поля:
   - `name`: `{domain}-{action}` за таблицею naming convention
     (`skill-creator-framework` → Naming Conventions).
   - `description`: формальний опис + push-тригери мовою Марка (українською,
     і якщо Mark реально й так пише — додати рос-варіанти фраз), плюс явний
     негативний тригер ("НЕ trigger на...") якщо є сусідній скіл, з яким легко
     сплутати.
   - Parent: чи є базовий скіл для успадкування (`core` для poster/publisher,
     `purchase-helper` для shopping, `cowork-prompt` для будь-якого `cowork-*`).
   - Чи володіє станом → чи потрібна секція `## Encapsulation`.
4. Видає **чорновий YAML-frontmatter + одне речення про структуру body** —
   це передається в `skill-creator` для повного скафолдингу файлу. Сам
   skill-rosetta файл не пише.

## Приклади перекладу

- *"хочу щоб воно саме тягнуло профіль клієнта з нотіону коли я кидаю імейл"*
  → domain `notion`, action `client-lookup` → `notion-client-lookup`;
  тригери: "хто цей клієнт", "профіль клієнта", наявність email-адреси в
  повідомленні разом із контекстом клієнта/проєкту.
- *"зроби щоб воно розуміло коли я скидаю скрін помилки і одразу гуглило що це"*
  → перевірити спершу: чи не покрито це вже загальним web-search поведінкою
  (не потрібен окремий скіл) чи `engineering:debug`-подібним патерном → якщо
  дійсно є Марк-специфічний воркфлоу зверху (куди зберігати, який формат
  відповіді) — новий `error-screenshot-triage`.
- *"кожного разу як я кидаю лінк на support-сайт і кажу зроби з цього гайди"*
  → це вже існуючий `helpcenter-digest` — використати його, не створювати новий.

## Коли НЕ перекладати

Якщо Mark вже дав готову назву скіла і опис/тригери своїми словами достатньо
конкретно (фактично вже написав чорновий SKILL.md розмовною мовою) — це вже
переклад, іти напряму в `skill-creator`, не дублювати крок.

## Формат відповіді

Коротко: 1) match знайдено / не знайдено (і чому), 2) якщо не знайдено —
чорновий `name` + `description` одним блоком, готовий вставити в
skill-creator. Без розлогих пояснень процесу перекладу.
